19  Проверка целостности

Авторы

Афоненко Анатолий

Войтович Елизавета

При получении файла важно установить, соответствует ли он ожидаемой версии. Но совпадение байтов ещё не отвечает на вопросы о правильности содержания и о том, кто выпустил файл. Сначала определим, что именно проверяет система.

19.1 Допустимое состояние

Требование целостности задаётся назначением данных. Для опубликованного архива это сохранение утверждённых байтов; для базы заказов — допустимые значения и связи записей. Работающая система изменяет данные, поэтому нужны требования и к состоянию, и к изменениям.

Определение 19.1 (Статическая целостность) Статическая целостность — соответствие состояния данных заданным ограничениям в рассматриваемый момент.

Например, цена товара положительна, код уникален, а заказ ссылается на существующего покупателя. Эти условия можно проверить по текущим данным.

Определение 19.2 (Динамическая целостность) Динамическая целостность — соблюдение заданных правил перехода от одного состояния данных к другому.

Заказ переводят из состояния «собран» в состояние «отправлен» после оформления отправки. Оба названия допустимы сами по себе, но для проверки перехода нужно знать ещё и выполненное действие. Такое различие помогает выбирать проверку: ограничения базы проверяют значения и связи, а программа должна соблюдать правила изменения заказа.

19.2 Хеш файла

Криптографическая хеш-функция вычисляет по точным байтам файла значение фиксированной длины. Обозначение H(F)H(F) означает применение выбранной функции HH к байтам файла FF. Например, SHA-256 выдаёт 256 бит, то есть 32 байта: при шестнадцатеричной записи это 64 знака.

Одинаковые входные байты дают одинаковый результат. Хеш используют для сравнения, но из него нельзя прочитать исходный документ. Свойства хеш-функции определяют, насколько трудно подобрать другие данные для подмены.

19.3 Сравнение с эталоном

Определение 19.3 (Эталон целостности) Эталон целостности — сведения об ожидаемом состоянии данных, с которыми сравнивают результат проверки.

Для файла FF вычисляют криптографический хеш H(F)H(F) и сравнивают с эталонным значением hh. Здесь FF — точные байты полученного файла, HH — выбранная хеш-функция, hh — сохранённый хеш ожидаемой версии. При стойкой функции совпадение даёт практическое основание считать, что получен файл, соответствующий эталону. Несовпадение обнаруживает расхождение, но не объясняет его причину.

Важно, откуда взят hh. Если нарушитель заменяет и файл, и опубликованный рядом хеш, ему достаточно вычислить хеш своего файла. Взламывать функцию для этого не требуется. Поэтому эталон получают доверенным способом: например, заранее сохраняют хеш известного выпуска отдельно от загрузки. Другой способ — проверять цифровую подпись по известному ключу издателя.

Хеширование проверяет соответствие эталону. Оно не определяет, безопасна ли программа и верны ли утверждения документа. Обнаружение изменения также не восстанавливает прежний файл: для восстановления нужна его копия.

19.4 Хеш опубликованного выпуска

На странице выпуска PowerShell v7.4.6 в GitHub разработчики опубликовали раздел SHA256 Hashes of the release artifacts и файл hashes.sha256. Для установщика PowerShell-7.4.6-win-x64.msi указано значение:

ED331A04679B83D4C013705282D1F3F8D8300485EB04C081F36E11EAF1148BD0

Для скачанного файла такой хеш можно вычислить в PowerShell:

Get-FileHash .\PowerShell-7.4.6-win-x64.msi -Algorithm SHA256

Значение поля Hash сравнивают с опубликованным для этого имени файла. Совпадение связывает скачанные байты с выбранным эталоном; основание доверия к странице выпуска проверяется отдельно.

19.5 Источники

Применение хеша для проверки файла разобрано в The Structure of Secure Systems, § 3.1. Опубликованные значения взяты со страницы PowerShell v7.4.6; команда проверки описана в справке Get-FileHash. Примеры ограничений базы соответствуют документации PostgreSQL.
