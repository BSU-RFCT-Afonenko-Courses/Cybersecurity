## Демонстрация и доступ к решениям

Демонстрационной сделать существующую задачу «Аудиторная задача 2. «Что именно нарушили?»». В ней уже есть пять ситуаций и полный короткий ключ. Это позволяет выполнить требование об открытом решении, не составляя нового ответа. Подготовительную задачу об образовательном портале сохранить отдельной: готового ключа в источнике нет.

Точная форма для `task/fundamentals/cia-cases.qmd`:

````qmd
---
course-presentation:
  answers: expanded
---

# КЦД {#sec-fundamentals-cia-cases}

:::: {#exr-fundamentals-cia-cases course-role="demonstration" difficulty="introductory" statement-visibility="open"}
## Аудиторная задача 2. «Что именно нарушили?»

<!-- Здесь дословно строки 103–108 М1. -->

::: {#sol-fundamentals-cia-cases}
<!-- Здесь дословно строки 109–114 М1 вместе с заголовком «Ключ». -->
:::
::::
````

Это схема размещения, а не готовое условие; комментарии не переносятся вместо текста. `target: manual` наследуется из `_metadata.yml`. Именованное решение связано по одинаковому суффиксу и находится в том же QMD. Для него не задаются `for=`, `course-role`, `when-format` или `when-meta`.

Три независимых условия публичной демонстрации: `statement-visibility="open"`, `course-role="demonstration"` у канонической задачи, фактически доступный контейнер решения. Стадия `demonstration` на странице семинара назначает задачу, но сама решение не открывает. `answers: expanded` дополнительно делает доступный разбор сразу раскрытым на странице этой задачи; разрешение публикации задаётся моделью Core.

Ключи остальных девяти решённых задач помещаются в один связанный `#sol-<суффикс>` в QMD соответствующей задачи. В `student` эти решения исключаются, в `full` доступны. Десять исходных ключей распределяются так: один публичный демонстрационный и девять преподавательских; у подготовительной задачи решения нет.

`.grading-notes` можно использовать внутри задачи только для уже имеющихся указаний по проверке, если они отделяются от решения без переписывания. Дополнительные критерии не сочинять. `.notes`, свёрнутый callout и HTML `details` не являются механизмами закрытого доступа.

## Применение учебных блоков

Использовать семантическую роль только для уже существующего фрагмента, которому она соответствует. Новые цели, выводы, ограничения, подсказки и критерии не писать ради заполнения шаблона.

| Исходный материал | Допустимая форма |
| --- | --- |
| Определение и следующее объяснение | Обычные абзацы, выделение термина, тематический заголовок |
| Готовый пример | Обычный абзац либо `#exm-*`; условие и объяснение сохраняются вместе |
| Готовый итог М1, строки 49–53 | `::: {course-role="takeaway"}` вокруг существующего блока |
| Предупреждение о различии события и инцидента | `course-role="misconception"` только если выделяется исходный текст целиком; исходный разбор из ключа остаётся при своём решении |
| Существующая справка аудита | Внутри условия рядом с заданием, с исходным заголовком и T6; её нельзя скрыть вместе с ключом |
| Подготовительные знания и чтение | `course-role="prerequisites"` и `course-role="reading"`, если такой текст уже есть; это не стадия подготовительной задачи |
| Подсказка | `.callout-tip` внутри задачи или рядом с `for="exr-ID"` той же страницы, только для исходной подсказки; полный ключ подсказкой не объявлять |
| Готовые требования к сдаче и проверке | `course-role="deliverables"` / `course-role="criteria"`; новые требования не добавлять |

У Core нет специальных учебных ролей `sources` и `references`. Сохранять исходные гиперссылки как обычные ссылки Markdown. Библиография `references.bib` доступна, но заменять исходные упоминания законов новыми ссылками `[@...]` и дописывать библиографические сведения в этой партии не требуется.

Модель и усилие передавать явно при создании агента. В текущем `collaboration.spawn_agent` задавать одновременно `fork_turns="none"`, `model` и `reasoning_effort`: переопределение модели или усилия при полном наследовании истории здесь не допускается. Передавать изолированному агенту необходимые пути и ограничения в задании. В конфигурации Codex соответствующий параметр усилия называется `model_reasoning_effort`. Если модель и усилие явно не задать, возможно наследование настроек родителя. Основание общих настроек: [официальная документация Codex об агентах](https://learn.chatgpt.com/docs/agent-configuration/subagents); ограничения вызова сверять с фактической схемой инструмента следующего запуска.

Исполнителей записи запускать последовательно: ресурсы и учёт → первое занятие → его интеграция и проверка → второе занятие → его интеграция и проверка → перенос М3 по связным активностям с интеграцией и проверкой каждой. В конце каждой активности её профильные списки, презентацию и оглавления обновляет агент интеграции, затем независимый проверяющий сверяет точность переноса. Координатор делает отдельный коммит завершённой активности до начала следующей. Разметчики общие файлы не изменяют. Проверки чтением можно вести параллельно по независимым файлам; сборки `student → full → student` и экспорты в общих каталогах выполняет один агент последовательно. Учитывать фактический лимит параллелизма среды; в текущем чате — четыре активных агента вместе с координатором.

Каждый исполнитель получает свою часть карты и обязательные ограничения, а не полную историю обсуждения. В отчёте: изменённые пути, покрытые локаторы, проведённые проверки и нерешённые технические вопросы. Координатор хранит журнал исполнения с выполненными партиями, SHA коммитов и результатами review; после перезапуска не повторяет уже завершённую работу.

Агент сборки при неуспехе передаёт журнал диагносту; повышение усилия применяется к диагностике, а не к повторному запуску той же команды без новой причины. Критерии приёмки и состав исходного текста при этом не меняются.

## Коммиты по связным активностям

Единица коммита — законченный семинар или другая связная активность, а не отдельный файл или работа одного агента. Семинарский коммит включает соответствующие теорию, банк, назначения, ресурсы, авторские метаданные и навигацию после интеграции и проверки. Подготовку импорта и общие технические исправления при необходимости оформлять самостоятельными связными коммитами с понятным русским сообщением.

Для М1 и М2 должны быть отдельные коммиты первого и второго занятий. Для М3 создавать отдельный коммит на каждый фактически содержащийся в нём семинар или другую связную активность; число таких коммитов не предполагать заранее. Не смешивать в одном коммите два самостоятельных занятия и не откладывать всё наполнение до единственного финального коммита. SHA и покрытие каждой активности записывать в журнал исполнения.
