# План изменений курсов и документации

План объединяет решения об учебной модели, сборке составного курса, презентациях, документации расширений и стартовых курсах. Цель — дать автору понятные настройки и воспроизводимые примеры, которые можно изучить на сайте, скачать и использовать самостоятельно.

Состояние обсуждения на 6 октября 2026 года. Это архитектурный план для согласования. Принятые решения приведены отдельно от предложений и открытых вопросов. Подробные планы реализации по репозиториям составляются после обсуждения соответствующих интерфейсов.

## Принятые решения

| Область | Решение |
| --- | --- |
| Банк заданий | Канонические задания и проверочные работы курса сосредоточены в отдельном book-проекте. Теория и презентации используют ссылки QRC. |
| Идентификаторы | Переработать `course.id` вокруг устойчивого владельца банка и экспортируемых заданий. Обычное учебное оформление вне банка должно работать без искусственного ID проекта. Точный способ объявления банка ещё обсуждается. |
| Состав курса | Заменить `course-site.projects` с полями `id`, `path`, `format`, `mount` простым списком путей вложенных проектов. Имя нового ключа ещё обсуждается. |
| Формат | Получать эффективный формат из конфигурации вложенного Quarto-проекта с учётом выбранных профилей. Не выбирать произвольно один из нескольких форматов. |
| Презентация | Сохранить одно основное содержание слайдов, одну презентацию и один результат рендера для аудитории и самостоятельного изучения. |
| Раскрытие материала | Скрытие и раскрытие подсказок, решений и общих заметок относится к отображению. Состав публичных ответов, начальное состояние и печать требуют уточнения. |
| Заметки | Общие заметки публичны. Дополнительных заметок только для преподавателя не будет. |
| Библиография | Общая база источников находится в корне каждого курса; вложенные проекты могут обращаться к `../references.bib`. Представление библиографии у проектов самостоятельное; единая нумерация не требуется. |
| Документация | Основной репозиторий шаблона становится обычным Quarto-сайтом документации: возможности, модель расширений, особенности, Markdown, итоговый рендер и доступный `.qmd`. Публикация — GitHub Pages. |
| Каталог примеров | Включить базовый курс, презентации, раздатку, PrairieLearn, Cloud и Moodle. Группировать по подключаемым расширениям; показывать обязательные и опциональные компоненты. |
| Языковые среды | Примеры могут требовать Java и Gradle, C++ и CMake, Python, Julia или R. Центральная сборка документации должна обходиться без установки всех этих сред. |

Имена каталогов конкретного курса не являются архитектурным контрактом. В текущем рабочем дереве есть `theory`, `task` и `seminars`; корневая конфигурация ещё ссылается на `practice`. При миграции нужно сверить фактические пути, сохраняя необходимые QRC namespace и ID целей.

## Предлагаемое распределение ответственности

| Владелец | Что хранит | Что собирает |
| --- | --- | --- |
| Репозиторий документации | Руководство, страницы расширений, каталог примеров, правила публикации | Документацию и общую публикацию из подготовленных примеров |
| Репозиторий расширения | Код, небольшой самостоятельный курс для демонстрации, проверки | Расширение и его примеры в нужных средах |
| Репозиторий полного шаблона | Курс с собственной программой, проектами заданий и инфраструктурой | Полный курс и проекты заданий |

Минимальные примеры предлагается держать рядом с расширением. Отдельный репозиторий полного шаблона появляется при самостоятельном составе зависимостей, владельце или цикле обновления. Разделение по Java, C++, Python, Julia и R — возможная организация полноценных шаблонов; создавать репозиторий для каждой комбинации языка и расширений не требуется.

Сайт документации получает готовые результаты из явно выбранных выпусков. Размещение демонстраций внутри одного сайта или на сайтах расширений пока открыто. В первом случае центральная сборка размещает подготовленные файлы; во втором QRC связывает публикации через импортируемые каталоги.

Каждый пример имеет две характеристики: набор расширений и среду сборки. Их следует показывать отдельно. Наличие пакета в bundle, активация фильтра или плагина и обязательность для результата также имеют разные значения.

## Этапы изменений

### Этап 0 Согласованная база и границы миграции

- [ ] Выбрать исходный согласованный набор версий: опубликованная поставка шаблона либо следующий совместимый выпуск расширений.
- [ ] Сопоставить установленные байты, API и схемы с выбранными исходниками репозиториев. Не переносить изменения в поставщика по путям из другого поколения архитектуры.
- [ ] Зафиксировать новые публичные настройки, значение владельца банка и порядок перехода со старой конфигурации.
- [ ] Сверить фактические каталоги, главы, ресурсы, профили и ссылки курса. Изменения рабочего дерева пользователя сохранить.

Результат: один определённый контракт и карта изменений по репозиториям. Каждая документируемая возможность относится к конкретной поставке.

В точном архиве шаблона `v1.0.0` Print и Moodle имеют версию `0.1.1` и контракт `course-body-package-v1`. Соседние локальные checkout описывают более ранние варианты. Оценки возможностей раннего Moodle P0 нельзя переносить на эту поставку. Успешный экспорт файла и проверенный импорт на реальной платформе остаются разными результатами.

### Этап 1 Учебная модель и владелец банка

- [ ] Разделить обычное учебное оформление и канонические данные банка в Core.
- [ ] Требовать устойчивого владельца для экспортируемых заданий и работ. Сохранить ключи вида `owner/exr-id` при переносе файлов.
- [ ] Убрать обязательность искусственного `course.id` у портала, теории и презентаций.
- [ ] Согласовать явное объявление банка, поведение `exr-*` и `assessment` вне него, допустимость второго банка в одном курсе.
- [ ] Сохранить независимость владельца банка, QRC namespace, ID цели и пути проекта.

Проверки результата: теория с учебными ролями без owner; банк без owner; перенос файла без смены ключа; повтор ID; задание вне банка; одинаковые ID в двух независимых курсах; состав работы с отсутствующим в выбранной проекции заданием.

### Этап 2 Простой состав курса и нативные форматы

- [ ] Ввести выбранный YAML-ключ со списком путей. Согласовать диагностику либо временную поддержку старой формы.
- [ ] Выводить внутреннюю идентичность и адрес размещения из нормализованного относительного пути, если это правило принято при обсуждении.
- [ ] Читать формат из эффективной конфигурации ребёнка с теми же профилями, с которыми он рендерится.
- [ ] Согласовать поведение нескольких форматов, пользовательских HTML-форматов и дополнительных PDF-результатов.
- [ ] Сохранить проверки пересечений источников и outputs до очистки каталогов.
- [ ] Сохранить сборку нативных книг и презентаций, связывание QRC и выбранную область общего поиска.

Проверки результата: строковая и словарная форма `format`; профиль меняет формат; несколько форматов; `a/slides` и `b/slides`; `./task` и `task`; вложенные пересекающиеся проекты; symlink; output внутри другого источника; переименование каталога; GitHub Pages с префиксом имени репозитория.

Самостоятельный рендер ребёнка может ограниченно откладывать ссылки на соседние проекты. Итоговая публикация должна проверять их полностью. QRC поддерживает ссылки в HTML и Revealjs; подготовка PDF или экспорт в платформу имеет отдельный маршрут.

### Этап 3 Единая публичная презентация

- [ ] Определить публичную проекцию презентации: какие ответы и подсказки присутствуют в одном HTML и доступны для раскрытия.
- [ ] Согласовать эту проекцию с Core: фильтрация до Presentation не должна удалять материал, который обязан раскрывать интерфейс.
- [ ] Заменить выбор разной разметки `study` и `lecture` при сборке единым представлением с настройкой отображения.
- [ ] Включить общие `.notes` в единый результат; убрать их зависимость от `.when-full`.
- [ ] Согласовать начальное состояние, отдельность настроек заметок и ответов, сохранение состояния и приоритет адресной ссылки.
- [ ] Согласовать поиск, обзор слайдов, историю, раскрытие по QRC и локальному якорю.
- [ ] Определить состав обычной печати, Reveal PDF и поведение после закрытия печати.

Проверки результата: переключение одного HTML без повторной сборки; неизменные порядок, ID и основное содержание слайдов; штатное окно заметок по `S`; переход к скрытому ответу; сохранение открытой цели после переключения; поиск и обзор; печать и восстановление экрана.

Публичная презентация не отменяет автоматически `student/full` для остальных материалов. Оформление скрытого блока не обеспечивает конфиденциальность. Состав платформенного экспорта определяется моделью, независимо от текущего состояния DOM.

### Этап 4 Общие ресурсы и переносимость

- [ ] Оставить общую библиографию в корне каждого курса, явно подключать её в компонентах.
- [ ] Включать в стартовый архив корень курса и все необходимые ресурсы: библиографию, CSL при его использовании, includes, изображения, проекты заданий и конфигурации.
- [ ] Согласовать способ выдачи отдельных `.qmd`: просмотр исходника, скачивание файла и полный стартовый архив.
- [ ] Проверять возможности AST при экспорте условий с цитатами, сносками и другими конструкциями; поддержка HTML сама по себе не гарантирует переносимость в Print или LMS.

Проверки результата: архив распакован в произвольном чистом каталоге; соседнего checkout нет; разрешаются все локальные пути; общий источник виден во всех компонентах; источник `.qmd` соответствует показанной версии.

### Этап 5 Сайт документации расширений

- [ ] Сделать обычный Quarto website с разделами возможностей, страницами расширений, руководством начала работы и каталогом примеров.
- [ ] Для возможности объяснять задачу, модель, YAML и Markdown, результат, ограничения форматов и необходимые зависимости.
- [ ] Показывать небольшие примеры разметки рядом с результатом. Использовать штатное экранирование Markdown, исполняемых блоков и shortcodes.
- [ ] Предоставить полный `.qmd` и необходимые файлы каждого законченного примера.
- [ ] Согласовать способ живых демонстраций канонических заданий: ссылки или встраивание результата из банка, чтобы пример в руководстве не создавал вторую декларацию того же задания.
- [ ] Подготовить матрицу «необходим для результата», «входит в bundle», «активируется конфигурацией».
- [ ] Отдельно показывать требования для просмотра, рендера документов, экспорта и исполнения проекта задания.

Проверки результата: каждый опубликованный фрагмент соответствует работающему примеру; показанный исходник можно получить; заявленные команды выполняются в чистом окружении; каталог не выдаёт экспериментальные или непроверенные операции за завершённую интеграцию.

### Этап 6 Курсы примеры и языковые среды

- [ ] Подготовить группы основ курса, представления материалов и платформенных адаптеров.
- [ ] Включить базовый курс, презентацию, обычную PDF-раздатку и раздатку из банка заданий, PrairieLearn, Cloud и Moodle.
- [ ] Повторяющиеся учебные фрагменты хранить в одном месте у владельца примеров. В выдаваемый архив включать необходимые файлы внутри самого курса.
- [ ] Определить минимальную матрицу сочетаний расширений и языковых сред для первого выпуска.
- [ ] У каждого исполняемого примера определить собственную сборку и проверки. Использовать штатные файлы Gradle, CMake, Python, Julia и R.
- [ ] Разделить задачи CI по средам; каждый job устанавливает только свои инструменты и нужные зависимости Quarto.
- [ ] При проверке расширения собирать пример с установленной поставкой кандидата; при публикации закреплять совместимые версии зависимостей.

Проверки результата: Java-проект действительно проходит Gradle; C++ — выбранную сборку CMake и проверки; Python, Julia и R — свои исполняемые примеры. Наличие файлов сборки и успешный HTML недостаточны для этих утверждений. Выполнение виртуальной машины и обмен с реальной LMS подтверждаются отдельно, если включены в обещание конкретного примера.

### Этап 7 Передача результатов и GitHub Pages

- [ ] Согласовать размещение демонстраций и область поиска: внешние сайты или готовые файлы внутри общей публикации.
- [ ] Передавать HTML, ресурсы, каталог QRC, исходники и стартовый архив из одной ревизии и проекции.
- [ ] Закреплять выбранный выпуск примера. Сведения о ревизии, версиях и сборке хранить рядом с пакетом, не расширяя JSON-контракт QRC произвольными полями.
- [ ] Согласовать адреса QRC для опубликованного сайта и локального preview. Текущий импорт требует абсолютный HTTP(S) `base-url` с завершающим `/`.
- [ ] Готовить публикацию из текущих успешных результатов в чистом staging; удалённые страницы не переносить из предыдущего выпуска.
- [ ] Публиковать штатным workflow GitHub Pages. Сборка центральной документации получает готовые примеры и не устанавливает все языковые среды.

Проверки результата: страницы, каталог и исходники одной версии; ссылки внутри книги и на слайды; PDF и архивы доступны; локальный preview; недоступный пакет даёт понятную ошибку; неудачная сборка не публикует старый результат как новый; удалённые материалы исчезают из QRC и поиска.

### Этап 8 Миграция действующего курса и документации

- [ ] Обновить установленную поставку после выпуска согласованных изменений поставщиков.
- [ ] Перевести состав курса на новый список путей и убрать owner из компонентов, которые им не владеют.
- [ ] Сохранить устойчивые ID банка и ссылки QRC, учесть текущие переименования каталогов.
- [ ] Применить общую политику заметок и настройку раскрытия презентации.
- [ ] Привести README, UPSTREAM и памятку по оформлению к фактической структуре и новым командам.
- [ ] Проверить действующий курс на выбранной поддерживаемой версии Quarto и согласованных профилях, затем публикацию.

Текущий локальный workflow уже рендерит сам курс и загружает `_site-student`. Переработка публикации документации относится к репозиторию шаблона; свойства его прежнего workflow нельзя автоматически приписывать локальному курсу.

## Порядок выполнения

Этап 0 предшествует изменениям интерфейсов. Этапы 1 и 2 определяют основу миграции. Этап 3 зависит от согласованной политики публичной проекции, этап 4 — от границ упаковки и экспорта. Документация этапа 5 и минимальные примеры этапа 6 развиваются по мере появления совместимых выпусков. Этап 7 объединяет их результаты. Этап 8 выполняется после проверки и выпуска нужных поставщиков.

Каждый этап завершается самостоятельным проверяемым результатом. Изменения разных поставщиков следует поставлять отдельными согласованными выпусками; готовность общего сайта не заменяет их проверки.

## Недочёты и пограничные случаи

| Приоритет | Случай | Требуемая обработка или открытое решение |
| --- | --- | --- |
| Высокий | Удалён только YAML `course.id`, но owner обязателен в сборке фактов, CUE и релизах | Переработать весь контракт владения, отделив педагогическое оформление от банка. |
| Высокий | `exr-*` объявлен вне банка | Явно выбрать диагностику и допустимую форму обычного учебного примера. Имя каталога не определяет семантику. |
| Высокий | Новый путь меняет URL публикации | Согласовать политику переименований и сохранения ранее опубликованных адресов. Owner и namespace сами не сохраняют URL. |
| Высокий | Несколько форматов или профиль меняет формат | Получать native effective config; либо диагностировать неоднозначность, либо согласовать отдельную поддержку результатов. |
| Высокий | Output пересекается с исходниками или другой проекцией | Проверять все пути до удаления файлов; учитывать нормализацию и symlink. |
| Высокий | Core удаляет ответы до рендера презентации | Определить публичную проекцию и переделать фильтрацию. Browser toggle не восстанавливает отсутствующий текст. |
| Высокий | QRC ведёт внутрь закрытого блока, навигация показывает все fragments | Согласовать раскрытие конкретной цели, поиск и overview с единым состоянием Presentation. |
| Высокий | Печать либо экспорт неожиданно отличается от экрана | Задать отдельные правила печати и проекций экспорта, проверить их независимо. |
| Высокий | Публикуемый исходник содержит реальные закрытые ответы или ключи | Демонстрации используют специально подготовленные публичные материалы; проверять весь пакет, включая ZIP, JSON, XML и поиск. |
| Высокий | HTML, QRC и QMD взяты из разных ревизий | Выпускать их как один согласованный результат. Не подставлять произвольный `latest`. |
| Высокий | Документация описывает старую локальную ветку вместо установленного релиза | Проверять возможности выбранной поставки. Print/Moodle из template `v1.0.0` новее рассмотренных локальных P0 checkout. |
| Высокий | Успешный render принят за проверку Gradle, VM или LMS | В паспорте примера указывать отдельно рендер, исполнение проекта, экспорт и проверенный обмен с платформой. |
| Средний | Одинаковые `tasks` и `exr-*` у независимых курсов | Импортировать каталоги под разными aliases. Проверять коллизии с локальными namespace. |
| Средний | Каталог из опубликованного сайта используется на localhost | Выбрать правило `base-url` и preview; относительный base URL сейчас не поддерживается. |
| Средний | Все демо скопированы на сайт, но поиск видит только документацию | Явно выбрать область поиска и при необходимости объединять индексы. |
| Средний | `../references.bib` отсутствует в архиве ребёнка | Выдавать полный корень курса либо включать общую зависимость внутрь переносимого проекта с корректными путями. |
| Средний | В экспортируемом условии есть цитата или сноска | Проверить capability выбранного body export и адаптера; библиография не добавляет поддержку AST автоматически. |
| Средний | Пример требует `../../../quarto-course` или родительский collect hook | У пользовательского стартера все установленные зависимости и пути должны разрешаться внутри выдаваемого дерева. |
| Средний | `quarto use template` пропускает `.github` и `.gitignore` | Выбирать способ выдачи, соответствующий обещанию шаблона; полный ZIP и GitHub template проверить отдельно. |
| Средний | Передача пакетов требует сети при каждом preview | Предпочтительно готовить закреплённые локальные пакеты; отдельно описать первоначальную загрузку и последующие операции. |
| Средний | Старая страница остаётся после ошибки или удаления источника | Новый staging и публикация только текущего успешного состава; кеши вычислений не являются источником списка публикуемых файлов. |
| Средний | Матрица языков и расширений превращается в десятки одинаковых курсов | Минимальный набор демонстрирует самостоятельные возможности и среды; полный набор сочетаний не требуется. |

## Пакеты вопросов для обсуждения

| Пакет | Решения |
| --- | --- |
| 1 Границы и репозитории | Роль корневого репозитория; владельцы минимальных и полных примеров; база версий. |
| 2 Учебная модель и сборка | Объявление банка и `exr-*` вне него; новый YAML-ключ и URL по пути; неоднозначные форматы и профили. |
| 3 Единая презентация | Публичный состав ответов; начальное раскрытие и сохранение состояния; ссылки, поиск, печать и заметки. |
| 4 Публикация и исходники | Единый сайт или внешние демо; общий поиск и local preview; QMD, архивы и способы получения стартера. |
| 5 Первый выпуск и проверки | Первые сочетания расширений и сред; глубина проверки исполнения и LMS; совместимость старой конфигурации и порядок миграции. |

Ответы уточняют этот же план. Имя ключа, признаки банка, интерфейс переключателя и формат передаваемого результата не должны появляться в реализации раньше соответствующего решения.
