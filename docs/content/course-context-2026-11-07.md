## Задачи и ход рассуждения

Студенты быстро схватывают материал, когда преподаватель показывает логику рассуждения. Подробности нужны в той мере, в какой они меняют вывод или позволяют проверить его.

Нынешние технические задачи требуют пересмотра. Повторяющийся недостаток: автор заранее называет объяснение или перечисляет категории ответа, а студенту остаётся воспроизвести их. В длинных условиях объём часто создаётся количеством соглашений о специально придуманной системе.

Для содержательной задачи нужно определить самостоятельный шаг студента: объяснить наблюдение, сравнить варианты, найти контрпример, спрогнозировать последствия, выбрать действие или установить предел вывода. Разбор должен показывать, как этот вывод получается из фактов. Короткие вычислительные упражнения сохраняют свою роль; каждому из них не требуется вымышленное происшествие.

Банковский перевод как пример транзакции и искусственное сопоставление удаления файла Access с удалением записей отвергнуты пользователем как неподходящие фабулы. Предложенный пример Git также слишком рано сообщал, какие изменения правильные и какой результат нужен. Эти фабулы не считать образцами для следующего прохода.

Эти объяснения впервые размещены в нынешнем семинаре 7. Поэтому считать асимметричные механизмы пройденными по итогам семинаров 4–5 нельзя.

## Ожидания по асимметричным механизмам

По уточнению пользователя обязательный результат — уметь объяснять назначение ключей. Ручной расчёт RSA не считать обязательным: по опыту преподавателя даже пример на малых числах получается слишком большим. Для знакомства с механизмом подписи пользователь выбрал простую схему Лэмпорта и включил её в общее занятие с последующей корректировкой по результатам.

Одноразовая подпись Лэмпорта опирается на знакомые хеши и позволяет показать создание и открытую проверку подписи, а также последствия повторного использования ключа. Набросок модели и источники сохранены отдельно в `docs/content/topic-7-revision-notes-2026-11-07.md`. Включение в общее занятие не устанавливает отдельного требования рассчитывать эту схему на зачёте: подтверждённый результат зачёта пока относится к объяснению ключей.

Диффи—Хеллман на малых числах остаётся отдельным предложением для согласования общего секрета. Один пример не заменяет другой по назначению. Выбор Лэмпорта для общего разбора не означает выбора Диффи—Хеллмана. Теория и учебные задачи по этим заметкам ещё не изменены.

## Глубина блока сохранности

Пользователь определил приоритет: нужно понимать особенности инкрементного и других подходов к копированию и решать задачи на них. RAID требуется поверхностно: основной принцип и пара иллюстраций, без глубокого объяснения.

Рабочее наполнение практики по копиям:

- На одной истории изменений определить, что попадёт в полную, инкрементную и дифференциальную копии.
- Сравнить объёмы создаваемых копий; отдельно различать объём одной копии и всего хранилища, если это нужно для вывода задачи.
- Найти набор копий для нужного состояния и объяснить последствия недоступности необходимой копии.
- Различить сохранение текущего состояния и возможность возврата прошлой версии.

Это предложенная конкретизация выбранного приоритета. Самостоятельное проектирование инфраструктуры, формальные показатели допустимых потерь и времени восстановления не являются установленными требованиями. Расчёты всех уровней RAID и отдельную тренировку восстановления XOR не делать обязательной основой этого блока.

Для дальнейшей переработки пригодны `exr-data-integrity-backup-volume` и `exr-data-integrity-backup-chain` из `task/bank/data-integrity.qmd` на проверенном `origin/master`. Задания `exr-data-integrity-mirror-copy` и `exr-data-integrity-mirror-history` проверяют близкий результат; требуется содержательная переработка формулировок и устранение дублирования. Нынешняя 90-минутная работа `exr-data-integrity-backup` не определяет объём аудиторной практики в согласованном времени.

Важная предпосылка: зависимость копий должна следовать из заданной модели. В нынешних слайдах для истории правок A → B → A при копировании целых файлов безусловно потребованы все инкременты. При восстановлении конечного состояния более поздняя версия A может заменить раннюю. Для первого объяснения цепочки подходит история A → B → C из `exr-data-integrity-backup-chain`; нельзя переносить её вывод на произвольный формат копий без проверки.
