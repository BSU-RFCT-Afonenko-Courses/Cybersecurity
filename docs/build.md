# Сборка курса

## Зависимости

Для локальной сборки используется системный Quarto 1.11.6; CI настроен на версии 1.11.5 и 1.11.6.
Также нужны Python 3, Node.js
с `node:test` и Graphviz (`dot`). Python-пакеты устанавливаются из корня:

```sh
python3 -m pip install -r CI/requirements-visualizations.txt
```

Закреплённые расширения перечислены в
[UPSTREAM.md](../UPSTREAM.md). `CI/install-extensions.sh` повторно устанавливает
внешние пакеты, логотип и авторское расширение визуализаций
из `extensions/course-visualizations`; устройство последнего описано в
[его руководстве](../extensions/course-visualizations/README.md).

## Профили и результаты

```sh
bash CI/render.sh student
bash CI/render.sh full
```

`student` предназначен для публичного курса, `full` — для преподавательского
просмотра доступных решений. Оглавления обоих профилей содержат те же темы
и работы. Различия видимости определяет Course Core.

Корневая сборка создаёт `_site-student/` или `_site-full/` и собирает подпроекты.
Их отдельные результаты находятся в `theory/_output/`, `task/_output/`,
`seminars/_output/` под каталогом профиля. Перед рендером теории и слайдов
автоматически выполняется `CI/prepare-course-visualizations.py`:
подготавливаются SVG, модули и запрошенные банковские фрагменты.
Семинарные фрагменты содержат только условия; банковские решения не переносятся
на слайды. Составную сборку ведут штатные обработчики Course Site.
`CI/cleanup-quarto-mediabag.py` до и после рендера удаляет оставшиеся рядом
с QMD одноимённые HTML с метаданными генератора Quarto, а также пустые
`*_files/mediabag` и их опустевшие родительские каталоги. Так остатки
прерванной сборки не попадают в снимок исходников Core. HTML без маркера
Quarto, HTML без одноимённого QMD и непустые каталоги сохраняются.

В каждом проекте установлен `fail-if-warnings: true`. `CI/render.sh` сохраняет
вывод в `_generated/ci-logs/render-*.log`, трассу подпроектов — в `_generated/ci-logs/subprojects.jsonl`
и возвращает код завершения Quarto. Журналы находятся в служебном `_generated`,
чтобы текущая запись лога не изменяла снимок исходников Core. Исходный вывод нужен для диагностики;
само наличие слова `WARN` не заменяет проверку результата процесса.

Сборки выполняются последовательно. Во время работы Quarto нельзя менять
исходники, конфигурацию и документацию, в том числе из другого процесса:
нативная операция Core проверяет неизменность снимка проекта.

## Проверки

Выбирайте проверки по изменённому содержанию. Для готовых общих сайтов:

```sh
python3 CI/site.py _site-student _site-full
python3 CI/check-access-control.py site _site-student _site-full
python3 CI/check-slides.py _site-student _site-full
```

Первая команда проверяет страницы, локальные ссылки и исключение служебных
файлов. Вторая проверяет разделение решений банков между профилями с учётом
публичных демонстрационных разборов. Третья берёт список презентаций из
`seminars/_quarto.yml` и проверяет титул, тематические группы, короткие QRC-ссылки,
отсутствие решений и подключение Navigation. Она не измеряет размещение на экране.
Для уже собранных отдельных экспортов банка доступен ограниченный режим:

```sh
python3 CI/check-access-control.py site task/_output/student task/_output/full --targeted
```

Он не подтверждает состояние остальных частей курса.

Текущая нативная модель проверяется сразу после сборки соответствующего профиля:

```sh
bash CI/render.sh student
bash CI/check-model.sh student
bash CI/render.sh full
bash CI/check-model.sh full
```

Проверка использует публичный `withCurrentNativeOperation` установленного Core:
проверяет выпуск, связи учебных элементов и доступность их содержимого.
Состав работ и задач берётся из текущего нативного каталога; видимость
определяется разметкой и выбранным профилем. После следующей сборки
текущей становится уже новая операция.

Предметные проверки визуализаций находятся в `CI/visualizations/`:
тесты моделей — `*.test.mjs`, извлечение банковских фрагментов — `*.test.py`,
браузерные проверки — `*.browser.cjs`. Браузерные сценарии используют
Playwright/Chromium и HTTP-доступ к готовым страницам. Они не заменяются
открытием файлов через `file://`.

## Условия и внешние потребители

Core 9 не содержит прежнего универсального `entrypoints/export.ts`.
Обычная сборка курса проверяется через публичный native API; она не создаёт
Body-пакеты. Экспорт назначения для внешнего потребителя требует отдельной
интеграции с актуальным договором assignment Core.

Курс содержит ручные задания; наличие банка не означает наличие программного
проекта или `project-check`. Печатные варианты Typst собираются отдельно по
[инструкции бланков](../control-works/fundamentals/README.md).

## Просмотр и публикация

Готовый общий сайт открывается из `_site-student/index.html` или
`_site-full/index.html`. Объяснения, схемы и условия доступны без сервера.
Интерактивы OJS требуют HTTP-доступа; для них можно использовать Python HTTP-сервер.
`CI/preview-nginx.sh` позволяет обслуживать отдельные экспорты без переноса
в общий каталог. Оба способа описаны в [руководстве просмотра](../CI/README-preview.md).

Workflow `.github/workflows/pages.yml` задаёт проверки PR и `master`.
Действующий источник GitHub Pages — корень ветки `gh-pages`. После слияния
в `master` в эту ветку отдельно переносят содержимое проверенного
`_site-student`, сохраняя историю ветки и добавляя `.nojekyll`.
Профиль full, исходники и Body-пакеты не публикуются.

В workflow также предусмотрена публикация через GitHub Actions из `master`
при `COURSE_PUBLISH_PAGES=true`. Этот способ требует переключения источника
Pages на GitHub Actions и не обновляет `gh-pages`; при действующей настройке
он не используется. Обычные команды сборки и проверки не публикуют сайт.
