# Целостность данных {#sec-draft-integrity}

> **ЧЕРНОВИК Т3 для К4.** Текст подготовлен для отдельной рецензии.
> Он не принят и не перенесён в действующую теорию.

## Допустимое состояние {#sec-draft-integrity-state}

Целостность нужна, чтобы данные сохраняли требуемые свойства при хранении
и изменении. Требование зависит от назначения системы. Для опубликованного
архива важно соответствие утверждённой версии; для базы заказов — допустимые
значения полей и связи между записями; для перевода — правильное изменение
нескольких остатков. Поэтому «целостность» нельзя свести к запрету любых правок.

::: {#def-draft-static-integrity name="Статическая целостность"}
Статическая целостность — соответствие состояния данных заданным ограничениям
в рассматриваемый момент. Проверка использует сами данные и требования
к допустимому состоянию.
:::

В таблице товаров цена должна быть положительной, код — уникальным,
а ссылка из заказа — указывать на существующего покупателя. Такие ограничения
проверяются по состоянию базы. В SQL для них есть ограничения `CHECK`,
`UNIQUE` и `FOREIGN KEY`. Проверка соответствия файла сохранённому эталону
тоже относится к состоянию: получены ли ожидаемые байты.

::: {#def-draft-dynamic-integrity name="Динамическая целостность"}
Динамическая целостность — соблюдение заданных правил перехода от одного
состояния данных к другому. Проверка учитывает исходное состояние,
выполненное действие и полученный результат.
:::

Заказ можно перевести из состояния «собран» в состояние «отправлен» только
после оформления отправки. Оба названия допустимы по отдельности,
но этого недостаточно для допустимости перехода. Ограничения состояния
и ограничения перехода дополняют друг друга.

## Транзакция как опора {#sec-draft-integrity-transaction}

Пусть в учебной базе остатки двух счетов равны 80 и 20. Перевод 15
с первого на второй должен сохранить их общую сумму и изменить оба остатка.

| Наблюдаемое состояние | Первый счёт | Второй счёт | Общая сумма |
|---|---:|---:|---:|
| До перевода | 80 | 20 | 100 |
| Выполнено только списание | 65 | 20 | 85 |
| Перевод завершён | 65 | 35 | 100 |

Условие «остатки неотрицательны» выполняется во всех трёх строках.
Оно не обнаруживает незавершённый перевод. Правило операции требует
согласованного изменения двух записей.

Транзакция объединяет списание и зачисление в атомарную операцию:
фиксируются оба изменения либо ни одно. При откате остаётся исходная пара
80 и 20. Изоляция определяет взаимодействие с одновременными операциями;
её режим выбирают с учётом проверяемых правил. Сама транзакционная оболочка
не угадывает правильного получателя или суммы: их задают программа,
ограничения базы и правила доступа. Корректно зафиксированная ошибочная
команда всё равно может нарушить требование предметной области.

Классификация выше — учебное различие двух вопросов: «допустимо ли
состояние?» и «допустимо ли так его изменить?». Она не устанавливает два
отдельных алгоритма защиты. Ограничения базы, транзакции, разграничение
прав и контрольные значения решают разные части задачи.

## Контрольное значение {#sec-draft-integrity-reference}

::: {#def-draft-integrity-reference name="Эталон целостности"}
Эталон целостности — сведения об ожидаемом состоянии данных, с которыми
сравнивают результат проверки. Основание доверять эталону входит в условия
такой проверки.
:::

Для файла $F$ вычисляют криптографический хеш $H(F)$ и сравнивают его
с эталонным значением $h$. Здесь $F$ — точная последовательность байтов,
$H$ — выбранная хеш-функция, $h$ — заранее известное контрольное значение.
При стойкой функции совпадение даёт практическое основание считать,
что файл соответствует эталону. Несовпадение означает, что это соответствие
не установлено; оно само по себе не указывает причину расхождения.

Хеширование доступно любому и не содержит сведений о том, кто утвердил
эталон. Сначала следует установить, **с чем** сравнивают данные и на каком
основании доверяют этому значению. Контроль состояния не восстанавливает
утраченные данные: для восстановления нужен отдельный источник.

## Пара ключей {#sec-draft-public-key}

При симметричном шифровании участники используют общий секрет. Асимметричный
механизм распределяет возможности иначе: одну часть пары можно передавать
другим участникам, вторую защищают от раскрытия.

::: {#def-draft-public-key-pair name="Пара асимметричных ключей"}
Пара асимметричных ключей — связанные ключи, совместно созданные для
определённой криптографической схемы: открытый ключ можно распространять,
закрытый ключ должен оставаться секретным. Знание открытого ключа
не должно позволять практически получить закрытый ключ или выполнить
защищённую им операцию.
:::

Названия «открытый» и «закрытый» описывают режим хранения. Назначение пары
определяет схема. Не всякая пара поддерживает и шифрование, и подпись;
на практике ключи применяют для разрешённых им назначений.

| Назначение | Действие с открытым ключом | Действие с закрытым ключом |
|---|---|---|
| Шифрование получателю | Подготовить защищённый пакет для владельца пары | Расшифровать адресованный владельцу пакет |
| Цифровая подпись | Проверить подпись для данных и этой пары | Создать подпись данных |

В первой строке выбирают пару **получателя**: цель — ограничить чтение.
Во второй — пару **подписывающего**: цель — дать возможность открытой
проверки. Проверяющему подпись не нужно передавать закрытый ключ.
Подпись не скрывает содержание документа. Шифрование по общедоступному
ключу само по себе не устанавливает отправителя.

Например, ключ для отправки зашифрованной заявки принадлежит службе,
которая должна её прочитать. Ключ проверки подписи опубликованного
обновления принадлежит стороне, которая выпускает обновление. Это две
разные цели выбора ключа, даже если в обоих случаях говорят о паре.

Конкретное устройство подписи и установление принадлежности открытого
ключа рассмотрены в [следующем черновике](signature-certificates.md#sec-draft-signature).
Здесь не требуется ручной RSA или устройство гибридного шифрования.

## Источники для рецензии

Примеры ограничений и атомарной операции сверены с официальной документацией
[PostgreSQL 18: ограничения](https://www.postgresql.org/docs/18/ddl-constraints.html)
и [транзакции](https://www.postgresql.org/docs/18/tutorial-transactions.html).
Различие состояния и перехода — принятая учебная рамка этого черновика,
а не перевод терминологии PostgreSQL. Назначение ключей подписи сверено
с [Berkeley, § 5.1](https://securitybook.eecs.berkeley.edu/chapters/lec05.html#definitions).
